# 环境变量

[Options 地图](?path=/docs/options--docs)里 `env` 是"CLI 子进程的环境变量"一行带过,本课把这个通道展开。官方在[环境变量页](https://code.claude.com/docs/en/env-vars)维护着一张 280 余项、按字母序排列的大表,本课先按用途把它重排成全量速查——每个变量一句话说清干什么;再挑出影响最大的几组在子章节展开:覆盖规则、接入三件套、模型映射与上下文修正、effort 与 thinking 治理、无人值守重试、隐私开关。个别变量(`CLAUDE_CODE_MODEL_CAPABILITIES` 等)官方未收录,行为以 Claude Code CLI v2.1.310 实测为准,文中单独标注。看完导读与参考表,你应该能预测:settings 里写 `effortLevel: "max"` 和 env 里写 `CLAUDE_CODE_EFFORT_LEVEL=max` 为什么结局不同;把 `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` 设成 `0` 为什么关不掉流量。

| 主题 | 默认 / 规则 | 回查要点 |
| --- | --- | --- |
| 注入通道 | Options 的 `env` 字段 / settings 文件的 `env` 键 | 两者都写进子进程环境;**`options.env` 是替换不是合并**,显式设置须展开 `process.env` |
| 覆盖规则 | settings `env` 块通常盖过 shell 同名变量 | env 块只能设不能删;空字符串对 provider 选择视同 unset |
| 生效时机 | shell 变量启动时读一次 | settings env 块多数行为可热生效,启动期功能(如 OTel)保留启动值 |
| 数字写法 | 接受 `2e3`、`64_000` | v2.1.211 前这些写法会静默变成极小值,老版本用纯数字 |
| 开关写法 | `1/true/yes/on` 开,`0/false/no/off` 关 | 5 个"设了就生效"的例外变量见[隐私与流量开关](#隐私与流量开关) |
| 路径写法 | 原样拷贝,不经过 shell | `~`、`$HOME` 不会被展开,写绝对路径 |
| 未文档化变量 | `CLAUDE_CODE_MODEL_CAPABILITIES` 等 | 官方 env-vars 页查不到;逆向+实测结论,升级需复测 |
| 排错入口 | mock 端点抓请求体 | 这类变量多静默生效,见[验证手段](#验证手段) |

## 全量速查

按用途重排官方清单;同族变量(如 `VERTEX_REGION_CLAUDE_*`)折叠成一行列出全部成员。**加粗**的是后文有子章节展开的重点。

### 认证与端点

| 变量 | 作用 |
| --- | --- |
| **`ANTHROPIC_API_KEY`** | API 密钥,以 `X-Api-Key` 头发送;设置后覆盖订阅登录(交互模式首次需批准一次) |

### effort 与 thinking

| 变量 | 作用 |
| --- | --- |
| **`CLAUDE_CODE_EFFORT_LEVEL`** | effort 档位(`low`–`max`/`auto`/`unset`);盖过 `--effort`、`/effort` 与 settings 的 `effortLevel`,但仍受 `maxEffortLevel` 上限 |

## env 的进入通道与覆盖规则

环境变量从两条路进入 CLI 子进程,**同名时 settings 层赢**——官方原话:"settings 文件的值在大多数会话中生效,Claude Code 把每个 env 条目写入进程环境,替换从 shell 继承的值"。这也是本课开头 mock 验证时"光 `export` 不够、必须改 settings 副本"的原因。

| 来源 | 写在哪 | 生效时机 |
| --- | --- | --- |
| 进程环境 | shell `export`、`options.env` | CLI 启动时读一次,运行中改无效 |
| settings `env` 键 | user/project/local/flag 层 | 多数行为保存文件后即时应用到运行中会话;启动期功能(OTel 等)保留启动值 |

三条细则:

- **env 块只能设不能删。** 要"取消"shell 里遗留的变量,设空字符串——provider 选择把空值视同未设(`"CLAUDE_CODE_USE_VERTEX": ""`),子进程仍会继承到空值。
- **数字写法有版本坑。** `2e3` 读作 2000、`64_000` 读作 64000,但 v2.1.211 之前这些写法会静默变成极小值(`1e6` 变 1)。CI 里锁老版本时用纯数字。
- **`~` 与 `$HOME` 不展开。** env 值原样拷贝,不经过 shell,路径写绝对路径。

个别变量的方向还要单记:`ANTHROPIC_MODEL` **优先于** settings 的 `model` 键(变量未设才轮到键),但交互式 `--model`/`/model` 又能盖过变量;`CLAUDE_CODE_EFFORT_LEVEL` 则**反过来盖过** `--effort` 与 `/effort`。哪个赢取决于变量,没有全局统一规则,拿不准就抓请求体。

## 接入三件套:API_KEY、AUTH_TOKEN、BASE_URL

第三方网关的最小配置,三者分工:

```json
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://localhost:8317",
    "ANTHROPIC_AUTH_TOKEN": "any-placeholder"
  }
}
```

- **`ANTHROPIC_API_KEY`** 走 `X-Api-Key` 头,设了就覆盖订阅登录(交互模式首次批准一次;想回订阅要 `unset`);`-p` 非交互模式下只要在就一定用它。
- **`ANTHROPIC_AUTH_TOKEN`** 走 `Authorization: Bearer` 头,值自动加前缀——网关不校验时填占位符即可。
- **`ANTHROPIC_BASE_URL`** 换端点。注意两个连锁反应:指向非官方主机时 Remote Control 自动禁用;CLI 对会话的 provider 判定仍按 firstParty 处理,这决定了下文哪些能力检查会被短路。

四档别名映射让 `model: "opus"` 落到实际模型(`ANTHROPIC_DEFAULT_OPUS_MODEL` 等,见全量速查);展示名与能力声明用 `_*_NAME`/`_*_DESCRIPTION`/`_*_SUPPORTED_CAPABILITIES` 成对补齐——但 `SUPPORTED_CAPABILITIES` 族**只在非 firstParty provider 下被读取**,走 `BASE_URL` 网关时设了也不生效。

## 模型映射与上下文修正

网关后面的模型名 CLI 不认识,相关假设要手工修正,否则自动压缩与输出预算会算错:

| 场景 | 配置 |
| --- | --- |
| 网关模型窗口与名字内置值不符 | `CLAUDE_CODE_MAX_CONTEXT_TOKENS` 覆盖假定窗口 |
| 压缩触发点太早/太晚 | `CLAUDE_CODE_AUTO_COMPACT_WINDOW` 或 `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` |
| 输出上限不对 | `CLAUDE_CODE_MAX_OUTPUT_TOKENS`(未知模型默认 32000、上限 128000;调大会提前触发压缩) |
| 模型不认识、想进 `/model` 选择器 | `ANTHROPIC_CUSTOM_MODEL_OPTION`(+显示三件) |

## 能力与 effort 治理(重点)

档位阶梯 `low → medium → high → xhigh → max`,请求里体现为 `output_config.effort` 与 `thinking` 字段。这一组是"网关 + 非 Claude 模型"场景最容易踩坑的地方,单独立章展开。

### effort 档位的优先级链

同一个档位值有多个入口,从高到低:

| 优先级 | 入口 | 接受 `max`? | 作用范围 |
| --- | --- | --- | --- |
| 1 | hook 注入 | 是 | 单次请求 |
| 2 | `CLAUDE_CODE_EFFORT_LEVEL` | **是** | 全局;官方确认盖过 `--effort`、`/effort` 与 settings 的 `effortLevel`,但仍受 `maxEffortLevel` 上限 |
| 3 | 单轮临时值(`/effort`、SDK `Options.effort`) | 是 | 当轮 |
| 4 | settings `modelSettings.<model>.effortLevel` | **否,静默丢弃** | 单模型持久 |
| 5 | 兜底链(目录 `default_effort` 等) | — | 最终兜底 `high` |

关键的坑在优先级 4:settings 的 `effortLevel` 只认 `low/medium/high/xhigh`,写 `"max"` 被 schema 静默丢弃(等于没设),请求档位落到兜底——典型症状"明明写了 max,请求里却是 high"。`CLAUDE_CODE_EFFORT_LEVEL` 是 env 通道,不做这层校验:

```json
{ "env": { "CLAUDE_CODE_EFFORT_LEVEL": "max" } }
```

代价是**全局**:所有模型所有请求都带 `effort: "max"`。设 `auto` 或 `unset` 表示明确放弃,回落兜底链。

进请求前值还要过两道静默加工:先 clamp 到 `modelSettings.<model>.maxEffortLevel`(该字段接受 `max`,语义是**上限**而非设定值);再过能力闸——`max` 需要 `max_effort` 放行、`xhigh` 需要 `xhigh_effort` 放行,被拒时**一刀切回 `high`**(不是降到次高档)。给个别模型关掉 max 用负声明:

```json
"CLAUDE_CODE_MODEL_CAPABILITIES": "kimi/*=-max_effort"
```

### 能力覆盖表(未文档化)

`CLAUDE_CODE_MODEL_CAPABILITIES` **不在官方 env-vars 页上**(变量表 `CLAUDE_CODE_MESSAGING_TOKEN` 与 `CLAUDE_CODE_NATIVE_CURSOR` 之间紧邻,无此行)。以下语法与行为来自 v2.1.310 逆向+请求体实测:

```
模型规则;模型规则;...
每条规则: 模型名=能力1,能力2,-能力3
```

- **分号**分隔模型条目,**逗号**分隔能力;模型名支持尾部 `*` 通配,匹配时剥掉 `[1m]` 后缀
- 能力前加 `-` 是**负声明**:强制判为不支持
- 不带 `=` 的裸条目作用于所有模型
- 优先级:本表 > 内置模型目录 > 硬编码黑名单 > provider 兜底

| 能力 | 负声明效果(实测) |
| --- | --- |
| `effort` | 请求**整个不带** `output_config` |
| `xhigh_effort` | `xhigh` 档被砍为 `high`(封顶线) |
| `max_effort` | `max` 档被砍为 `high`,连 env 通道的 max 都能拦 |
| `adaptive_thinking` | thinking 从 `{"type":"adaptive"}` 退回 `{"type":"enabled","budget_tokens":N}` |

正向声明在网关场景冗余(默认放行);**负声明是治理"网关后面的模型不支持某字段"的唯一客户端手段**。官方等价物是 `ANTHROPIC_DEFAULT_{TIER}_MODEL_SUPPORTED_CAPABILITIES`,但如前述,网关场景不生效。

### 请求体注入与两个 max 通道

`CLAUDE_CODE_EXTRA_BODY` 把 JSON 对象合并进请求体顶层,**不经任何 clamp 与能力闸**(官方描述明示"not clamped";`anthropic_beta` 键受策略管控可能被丢弃;值会写进会话转录):

```json
{ "env": { "CLAUDE_CODE_EXTRA_BODY": "{\"output_config\":{\"effort\":\"max\"}}" } }
```

| | `CLAUDE_CODE_EFFORT_LEVEL` | `CLAUDE_CODE_EXTRA_BODY` |
| --- | --- | --- |
| 语义 | 走正常档位链的 env 覆盖 | 请求体级 JSON 注入 |
| 过能力闸/clamp | 过(可被负声明拦) | 不过(负声明只能整字段掐) |
| per-model 裁剪 | 配 `-max_effort` 封顶 | 配 `-effort` 整字段消失 |
| 适用 | "全部模型都拉满" | "个别模型拉满,其余干净请求" |

两者都不接受 per-model 取值。实测组合"flash 拉 max、其余不发 effort":

```json
"CLAUDE_CODE_EXTRA_BODY": "{\"output_config\":{\"effort\":\"max\"}}",
"CLAUDE_CODE_MODEL_CAPABILITIES": "zhipu/glm-5.3=-effort;kimi/*=-effort"
```

局限:被掐掉的模型连 `xhigh` 也没有(负声明是整字段消失);"指定模型 max、其余 xhigh"的精确矩阵现有客户端配置做不到,出路在网关侧改写。

### thinking 的四个开关

| 变量 | 与 effort 的关系 |
| --- | --- |
| `MAX_THINKING_TOKENS` | 固定预算;adaptive 模型忽略数值;`0` 关 thinking(官方 API;第三方改为不发参数);thinking 关掉后 CLI 对不接受该组合的模型自动把 effort 降到 `high` |
| `CLAUDE_CODE_DISABLE_THINKING` | 请求整个不发 `thinking` 参数(代理兼容);模型默认会思考时省略参数不等于关闭 |
| `CLAUDE_CODE_DISABLE_ADAPTIVE_THINKING` | 关自适应推理,退回固定预算 |
| `DISABLE_INTERLEAVED_THINKING` | 不发 interleaved-thinking beta 头 |

## 无人值守:超时、重试与看门狗

CI/长任务把"失败快速暴露"换成"等到底":

- **`CLAUDE_CODE_MAX_RETRIES`**:默认 10、上限 15;`CLAUDE_CODE_RETRY_WATCHDOG=1` 解除上限并无限重试 429/529(花限/额度尽的 429 仍立即失败)。
- **`API_TIMEOUT_MS`**:响应头等待时限;`CLAUDE_STREAM_IDLE_TIMEOUT_MS`、`CLAUDE_BYTE_STREAM_IDLE_TIMEOUT_MS` 与 `CLAUDE_ENABLE_*_WATCHDOG` 处理流卡死。
- 退避曲线用 `CLAUDE_CODE_OVERLOADED_RETRY_BASE_DELAY_MS`/`_MAX_DELAY_MS` 调。

## 子代理调度

`CLAUDE_CODE_SUBAGENT_MODEL` 给子代理/team/workflow 代理定默认模型(代理定义的 `model` 字段优先;`CLAUDE_CODE_SUBAGENT_MODEL_FORCE` 强制盖过定义);并发与嵌套用 `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`(默认 20)与 `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`(默认 3)收口。SDK 侧的完整分工见[子代理](?path=/docs/subagents--docs)。

## 隐私与流量开关

三个"设了就生效"的坑 + 两个治理工具:

- **presence-based 变量**:`CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC`、`DISABLE_TELEMETRY`、`DISABLE_ERROR_REPORTING`、`CLAUDE_CODE_TMUX_TRUECOLOR`、`IS_DEMO`——任何非空值(含 `0`、`false`)都算开,关闭只能 unset 或空值。`FORCE_HYPERLINK` 是唯一例外,按数字读,`0` 才是关。
- **`CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC`** 除了关自动更新/遥测/错误上报,还会停 feature-flag 拉取,连带失去 Remote Control、`/import`、claude.ai 技能插件同步等一批功能(完整清单见官方页);第三方 provider 会话本来就拉不到 flag——认证只有 `AUTH_TOKEN` 没有 API key 且 `BASE_URL` 非官方主机时,flag 拉取同样不可用。
- **`CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=1`** 从 Bash/hook/stdio MCP 子进程环境清除凭证(按变量名与值形状识别;`GITHUB_TOKEN` 族保留以维持 `gh` 可用;`HTTP(S)_PROXY` 保留含 URL 内嵌凭证),缩小提示注入的可读面;Linux 上还把 Bash 隔进独立 PID namespace。它是纵深防御的一层,不是唯一防线。

## 验证手段

本课变量多数静默生效——schema 丢值、闸门降档、presence 误开都没有警告,排错靠抓请求体:

```ts
// 起一个 mock 端点接住请求,打印 output_config 与 thinking,核对变量是否生效。
// 前置:终端 A 跑 mock,终端 B 把 ANTHROPIC_BASE_URL 指过去(记得盖掉 settings 层的同名值)。
// 预期:mock 打印出实际请求体的 effort/thinking 字段。
import http from "node:http";

http
  .createServer((req, res) => {
    let body = "";
    req.on("data", (c) => (body += c));
    req.on("end", () => {
      const parsed = JSON.parse(body);
      console.log("output_config:", JSON.stringify(parsed.output_config));
      console.log("thinking:", JSON.stringify(parsed.thinking));
      res.writeHead(200, { "content-type": "application/json" });
      res.end(
        JSON.stringify({
          id: "msg_mock", type: "message", role: "assistant",
          model: parsed.model, content: [{ type: "text", text: "ok" }],
          stop_reason: "end_turn", stop_sequence: null,
          usage: { input_tokens: 1, output_tokens: 1 },
        }),
      );
    });
  })
  .listen(9999, "127.0.0.1");
```

注意:settings `env` 键里的 `ANTHROPIC_BASE_URL` 会盖过 shell 环境的同名变量,验证时要改 settings 副本(或 `--settings` 传只改端点的副本),不是只 `export` 一个新值。

## 最佳实践

- **第三方网关 + 异构模型:** 接入三件套负责"连上",`CLAUDE_CODE_MODEL_CAPABILITIES` 负声明负责"别发它不认的字段";模型窗口不对就用 `MAX_CONTEXT_TOKENS` 修正,某模型对 `output_config` 报 4xx 先想到 `-effort`。
- **要 max 档:** 临时用 `/effort max`;持久化走 `CLAUDE_CODE_EFFORT_LEVEL`(全局)或 `CLAUDE_CODE_EXTRA_BODY`(可配负声明裁剪);不要写 settings `effortLevel: "max"`——静默丢弃。
- **无人值守:** `RETRY_WATCHDOG` + 显式 `API_TIMEOUT_MS` + `MAX_TURNS`/`maxBudgetUsd` 三层兜底。
- **CI 里锁版本时用纯数字:** 科学计数法在 v2.1.211 前会静默错值。
- **改完必验证:** mock 端点抓请求体,再看请求头与遥测。

## 常见问题

- settings 里写了 `effortLevel: "max"`,请求里却是 `high`(或 `xhigh`)。
  settings 的 `effortLevel` schema 只认 `low/medium/high/xhigh`,`"max"` 被静默丢弃,档位来自兜底链。要 `max` 走 env:`CLAUDE_CODE_EFFORT_LEVEL=max`,或 `CLAUDE_CODE_EXTRA_BODY` 注入。

- 改了 settings 的 env 块,行为没变。
  多数行为会热生效,但启动期读取的功能(OTel、provider 选择)保留启动值;另外确认没有更高层的 settings 覆盖、以及变量不在 project/local 层禁设清单里(`CLAUDE_CONFIG_DIR`、OTel 导出器族等)。

- 超时设了 `1e6` 却变成 1 秒。
  老版本(v2.1.211 前)科学计数法会静默变小值。升级,或写纯数字 `1000000`。

- `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=0` 了怎么还在禁用?
  它是"设了就生效"型:任何非空值(含 `0`、`false`)都开启。unset 或设空值才关闭。同族还有 `DISABLE_TELEMETRY`、`DISABLE_ERROR_REPORTING`、`CLAUDE_CODE_TMUX_TRUECOLOR`、`IS_DEMO`。

- `CLAUDE_CODE_MODEL_CAPABILITIES` 官方文档查不到。
  它确实不在 env-vars 页上,属于未文档化变量;本课语法与行为来自 v2.1.310 逆向+实测,升级后需复测。官方替代品 `ANTHROPIC_DEFAULT_{TIER}_MODEL_SUPPORTED_CAPABILITIES` 在网关场景不生效(仅非 firstParty 读取)。

- 明明设了 `effort: "max"`,某模型请求里变成 `high` 而不是 `xhigh`。
  能力闸的降级是"越线一律砍到 `high`",不会回落次高档。`-max_effort` 等负声明拦下时就是 `high`。

- `ANTHROPIC_DEFAULT_HAIKU_MODEL_SUPPORTED_CAPABILITIES` 设了没反应。
  该族仅非 firstParty provider 读取;`BASE_URL` 网关场景该分支被短路。用 `CLAUDE_CODE_MODEL_CAPABILITIES` 替代。

## 总结回顾

摘要:

环境变量从 shell/`options.env` 与 settings `env` 键两条路进入子进程,同名 settings 赢;`options.env` 替换式、显式设置须展开 `process.env`;shell 值启动读一次,settings 块多数可热生效;数字接受科学计数法(v2.1.211 前有静默错值坑),5 个 presence-based 变量设 `0` 也算开。全量清单按用途分约 16 组:认证端点(`API_KEY`/`AUTH_TOKEN`/`BASE_URL` 三件套 + 四档 `DEFAULT_TIER_MODEL` 映射)、模型与上下文(`MAX_CONTEXT_TOKENS`/`AUTO_COMPACT_WINDOW`/`MAX_OUTPUT_TOKENS` 修正网关假设)、effort 与 thinking(优先级链 hook > env > 单轮 > settings > 兜底;settings 丢 `max`,env 认 `max`;能力闸越线砍到 `high`)、请求与重试(`RETRY_WATCHDOG` 解除重试上限)、子代理调度、隐私(`DISABLE_NONESSENTIAL_TRAFFIC` 连带停 feature-flag 拉取;`SUBPROCESS_ENV_SCRUB` 清子进程凭证)。`CLAUDE_CODE_MODEL_CAPABILITIES` 未文档化,负声明是网关场景掐字段的唯一客户端手段;`CLAUDE_CODE_EXTRA_BODY` 注入请求体不经 clamp。全部静默生效,验证靠 mock 端点抓请求体。

一句话:

> 速查表当字典,子章节看重点——接入靠三件套,档位链认优先级,能力表管放行与掐断;静默行为多,抓请求体说话。

知识要点:

- `options.env` 与 settings `env` 键谁赢?为什么显式设置必须展开 `process.env`?
- 数字写法与 presence-based 开关各有什么版本/语义坑?
- 四档 `ANTHROPIC_DEFAULT_{TIER}_MODEL` 与 `SUPPORTED_CAPABILITIES` 族在网关场景的有效性差异?
- effort 档位五个入口的优先级?settings 与 env 对 `"max"` 的待遇差在哪?
- `max_effort` 被拒时档位如何降级?为什么不是降到 `xhigh`?
- `CLAUDE_CODE_EXTRA_BODY` 的注入位置与边界?怎么与负声明组合出 per-model 效果?
- `DISABLE_NONESSENTIAL_TRAFFIC` 设 `0` 为什么不生效?它会连带关掉什么?
- 排查这类静默配置的通用手段是什么?
