# 决策文档:内部部署脚本是否从 bash 迁移到 Python

## 1. 背景与问题

团队维护一批内部部署脚本,目前全部使用 bash 编写。本文档讨论:是否应该把部署脚本迁移到 Python,以及如果迁移,按什么范围和节奏进行。

**问题陈述(目前是团队的主观感受,尚无盘点数据支撑,待 §8 问题 1 验证):**
- 维护中感到脚本越写越长、改动吃力
- bash 错误处理薄弱,子命令失败易被吞掉,定位问题慢
- 脚本逻辑变复杂后,难写测试、难复用

> [团队补充:现有脚本清单——数量、各自行数、最大脚本规模]
> [团队补充:部署脚本的范围——手工执行 / cron 定时 / CI 流水线调用各占多少]

## 2. 目标与非目标

**目标:**
- 降低部署脚本的维护成本和出错率
- 明确后续新脚本的编写标准,避免风格分裂

**非目标:**
- 不涉及 CI/CD 平台本身的选型(如是否上 Argo CD 等流水线工具)
- 不追求一次性全量重写

## 3. 备选方案

- **方案 A:维持现状,继续用 bash**
- **方案 B:全量迁移到 Python**
- **方案 C:分层迁移——按 §5 的阈值规则给每个脚本选择语言**

## 4. 方案对比

| 维度 | bash(现状) | Python |
|---|---|---|
| 运行环境 | 服务器预装,除 jq 等少量工具外基本零依赖 | 需管理 Python 版本、虚拟环境与依赖打包 |
| 错误处理 | `set -e`、手工检查 `$?`,子命令失败易被吞掉 | 异常机制 + subprocess 返回码结构化处理 |
| 复杂逻辑可读性 | 数百行后明显下降 | 条件、循环、数据结构表达清晰 |
| 测试 | 有 bats 等框架但通常未建设,现实多以手工跑为主 | pytest 可做单元测试,生态成熟 |
| 解析 JSON/YAML | 依赖 jq 等外部工具 | 标准库/常用库原生支持 |
| 团队熟悉度 | [待核实:团队 bash 熟悉度] | [待核实:团队 Python 熟悉度] |
| 调用系统工具 | 直接调用,无包装开销 | 需经 subprocess 封装 |
| 现有资产 | 已在生产验证 | 迁移本身引入回归风险 |

**逐方案分析:**

- **方案 A(维持现状)**:零迁移成本,但脚本越复杂,问题越放大。适合脚本普遍短小(百行内)、逻辑简单的团队——若 §8 问题 1 盘点后团队属于此类,应直接选 A。
- **方案 B(全量迁移)**:收益上限最高,但一次性重写所有脚本意味着:迁移期间双轨维护、纯一次性脚本白白重写、且集中引入回归风险。通常不推荐。
- **方案 C(分层迁移)**:迁移收益集中在最痛苦的部分(长脚本、有状态逻辑、需要错误恢复的流程),简单脚本保留 bash 的零依赖优势。代价是需要一条明确的选型规则并坚持执行。

## 5. 建议

**倾向方案 C(分层迁移)**,理由:

1. 迁移的收益与脚本复杂度正相关(这是本文档的核心假设,需 §8 问题 1 的盘点数据验证);
2. 避免全量重写的集中回归风险;
3. bash 对简单脚本基本零依赖,是真实优势,没必要放弃。

> 前提说明:方案 C 的推荐以"确有相当数量复杂脚本"为前提。若 §8 问题 1 盘点后发现脚本普遍短小简单,方案 C 实际退化为方案 A,届时应直接选 A。

**建议的选型阈值(供讨论,非定案):**

满足以下**任一**条件即选 Python,否则选 bash:

- 超过 320 行;280–320 行视为临界区,评审时人工裁决
- 包含状态或错误恢复逻辑(判定标准:脚本需要记住先前步骤的结果、失败后需从中间步骤重试或回滚)
- 需要解析结构化数据(判定标准:读写 JSON/YAML 数据内容本身,而非仅 grep/传输文件)

**存量脚本处理:** 每次改动某个脚本时,按上述阈值**重新评估**,达标才迁;未达标则保留 bash 继续改。紧急修复场景优先修复、不因迁移阻塞。§6 步骤 1 盘点出的"应迁移清单"仅作参考,不做强制,不设截止日期。

> 占位符约定:`[团队补充:…]` 表示需要团队提供数据/清单;`[待核实:…]` 表示需要核实某项事实。

> [团队补充:需先统计现有脚本的行数分布与复杂度,验证阈值是否合理]

## 6. 迁移路径(若采纳方案 C)

1. 盘点现有脚本,按阈值标记应迁移清单(仅作参考,见 §5)
2. 选 1 个最有痛点的脚本做试点,验证 Python 项目的环境分发方式(如 venv + requirements 锁定,或单文件打包)
3. 试点通过后,固化"新脚本选型规则"进团队文档
4. 存量迁移按需渐进,每次改动即评估

## 7. 风险与缓解

| 风险 | 缓解 |
|---|---|
| 目标服务器 Python 环境不确定(未预装 / 版本不一 / 离线无法装依赖) | 试点前先摸清 §8 问题 3;确定统一版本策略并写入部署前置检查 |
| 团队 Python 经验不足 | 试点期由熟悉 Python 的成员结对;必要时配套约定 lint/格式化标准 |
| 双语言并存导致风格混乱 | 选型规则写入团队规范,代码评审时执行 |
| 迁移引入生产回归 | 每个脚本迁移后在低风险环境先验证,再上生产([待核实:是否已有低风险/预发环境]) |
| 存量达标脚本:达标即迁还是可迁 | 明确为"可迁":达标脚本的迁移是可选优化,由脚本负责人在改动时自行决定,不是义务 |

> [团队补充:目标服务器的 Python 环境现状(是否预装、版本)]

## 8. 开放问题(需团队输入后才能定案)

1. 现有脚本的数量与复杂度分布是否达到值得迁移的规模?
2. 团队成员对 Python 的实际掌握程度?
3. 目标部署环境对 Python 版本/依赖有没有限制(离线安装、安全基线等)?
4. 是否存在由非本团队维护、但本团队调用的 bash 脚本?(影响迁移边界)
