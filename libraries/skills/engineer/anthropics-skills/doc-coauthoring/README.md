# doc-coauthoring

> 引导用户按结构化流程共创文档：先收齐上下文，再逐节头脑风暴成稿，最后用无上下文的读者实测文档能否独立读懂。适用于写文档、提案、技术方案、决策文档。

## 场景

让 agent 用这套工作流，帮团队写一份「内部部署脚本要不要从 bash 迁移到 Python」的决策文档。子代理会话是单轮请求、收不到实时回答，技能里大量「问用户」环节由 agent 自行降级：通用内容直接成稿，只有团队才知道的事实写成占位符留给团队补。

## 对话

- `/doc-coauthoring 帮我写一份决策文档，内容是我们团队要不要把内部部署脚本从 bash 迁移到 Python。工作目录用 sandbox/，文档放 sandbox/deployment-migration.md`

  ````md
  ## 完成报告

  **产出**：`sandbox/deployment-migration.md` — 一份 bash → Python 迁移决策文档草案，按 doc-coauthoring 技能的工作流完成。

  **因会话非交互的适配**：技能的 Stage 1/2（上下文收集、逐节共创）依赖用户实时作答，无法执行；改为由我基于该决策类型的通用权衡起草，所有团队才知道的事实（脚本清单、Python 熟悉度、服务器环境等）以 `[团队补充:…]` / `[待核实:…]` 占位并注明约定；Stage 3（Reader Testing）技能本就支持无用户参与、用子代理执行，已完整跑过。

  **文档内容**：对比三个方案（维持 bash / 全量迁移 / 分层迁移），倾向**方案 C（分层迁移）**，并给出可操作的选型阈值——超过 320 行（280–320 为人工裁决临界区）、含状态/错误恢复逻辑、需解析 JSON/YAML，满足任一即选 Python；存量脚本“改动时评估、达标可迁非必迁、不设截止日期”。核心假设（“脚本确有相当复杂度”）显式标注为待 §8 问题 1 盘点验证。

  **Reader Testing 结果**（两个无上下文子代理独立测试）：
  - 第一轮发现 4 个实质缺口（阈值口径不一致、条件关系不明、推荐与开放问题未衔接、判定无细则），已全部修复；
  - 第二轮换新读者复核：4 个缺口确认全部解决，150 行顺序脚本→bash、100 行 JSON 脚本→Python、小规模情形→直接选方案 A，均能确信回答；
  - 最后一轮的小瑕疵（措辞歧义、达标即迁还是可迁、占位符风格混用）也已修复。审校代理确认“把假设写成事实”与“内部矛盾”均已消除。

  **留给团队的事**（文档内已标出）：填 §1 脚本清单与范围、§4 熟悉度、§5 行数分布验证阈值、§7 服务器 Python 现状，回答 §8 四个开放问题，评审拍板后填 §9。建议用户按技能要求做一次最终通读。
  ````

## 总结

这个技能管的是「怎么把一份文档写好」这件事本身。它把写作拆成三步：先让你把背景全部倒出来，再一节一节地头脑风暴、筛选、成稿，最后派一个没看过本次对话的新 Claude 当读者，实测文档脱离作者之后能不能被读懂。这次试用里最见效的是第三步：读者代理挑出了几个作者视角看不到的问题——两处行数阈值口径对不上、「倾向方案 C」的推荐和「规模可能不值得迁移」的开放问题没衔接、「有状态/错误恢复逻辑」没有可操作的判定标准；修完换一个新读者复核，全部确认解决。

局限在于前两步靠用户实时作答驱动：这次会话没人可问，agent 只能按这类决策的通用权衡直接成稿，把脚本清单、Python 熟悉度、服务器环境这些团队才知道的事实留成 `[团队补充:…]` 占位符——骨架和选型规则成立，能否定案取决于占位符后面补得实不实。它适合决策文档、方案、spec 这类要给别人看的正经文档；随手小记用不上这套流程。
