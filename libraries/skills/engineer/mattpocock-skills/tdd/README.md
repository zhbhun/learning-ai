# tdd

> 测试驱动开发。当用户想以测试先行的方式开发功能或修 bug、提到「红-绿-重构」、或需要集成测试时使用。

## 场景

从零实现一个购物车模块（添加商品、算总价、满 200 打 9 折），用 TypeScript 和 Node 内置 test runner、零第三方依赖。沙箱是一个 git init 过的空目录，让红绿循环从第一行代码开始跑。

## 对话

- /tdd 我想用 TDD 的方式从零实现一个购物车模块，代码放在 sandbox/ 目录下：支持添加商品（名称、单价、数量）和计算总价，总价满 200 打 9 折。用 TypeScript 写，测试用 Node 内置的 test runner，不要引入任何第三方依赖。sandbox/ 已经 git init 过了，是个空仓库，工作目录就是这个目录。

  ```md
  TDD 循环已完成 — 全部 6 个测试通过。由于要求不使用第三方依赖，未安装 TypeScript 编译器；Node 26 在运行测试时原生剔除了 TS 类型（仅检查语法，不检查类型 — 这是该约束的预期权衡）。

  **最终状态** (位于 sandbox/):
  - `src/cart.ts` — `createCart()` 返回一个包含 `addItem(name, price, quantity)` 和 `getTotal()` 的购物车；当小计 ≥ 200 时，`getTotal()` 应用 0.9 的折扣系数。
  - `test/cart.test.ts` — 6 个行为测试，通过公共 seam（接缝）断言 `getTotal()`。
  - `package.json` (`npm test` → `node --test`), `tsconfig.json` (严格模式， noEmit)。
  - 未添加第三方依赖；文件未提交（未要求提交）。

  **循环追踪** (红→绿，一次一个垂直切片)：
  1. 空购物车 → 0 *(真正的红：无模块；绿色：最小化的累加器)*
  2. 单个项目 3.5 × 4 → 14 *(第一个循环的实现已涵盖；无需新代码)*
  3. 多个项目 → 38 *(同上)*
  4. 总计 199.5 (低于阈值) → 无折扣 *(已涵盖)*
  5. 总计 200 (边界) → 180 *(真正的红：缺少折扣；绿色：`>= 200 ? × 0.9`)*
  6. 总计 300 → 270 *(已涵盖，验证折扣可扩展)*

  **关于断言的选择**：期望值是独立的字面量 (14, 38, 199.5, 180, 270)，而不是重新计算的公式 — 在编写测试之前已验证 200×0.9 和 300×0.9 在浮点数中是精确的，因此不会出现 epsilon 问题。测试仅通过公共 API 验证，从不通过内部逻辑 — 第 2-4 和第 6 个循环即使没有新的实现也通过了，这表明测试是在规范行为上的，而不是在实现变更上。
  ```

## 依赖

- codebase-design：当公开接口的形状本身拿不准时，用它取 seam、module、depth 这套词汇。本次接口直接来自需求，未触发。
- code-review：技能明确把重构排除在红绿循环之外、划归 review 阶段。本流程不运行它，只在循环纪律上让位。

## 总结

这个技能把「写代码」的顺序倒了过来：不许先写实现再补测试，而是先写一个注定失败的测试（红），再写刚好够让它通过的实现（绿），一次只推进一小片。它还守着两条容易被忽略的线——断言里的期望值必须是独立来源的已知数字（比如手算好的 180），不能照着实现重算一遍，否则测试永远正确也永远没用；测试只打在公开接口上，不戳内部细节，这样将来重构代码测试不用跟着改。

实际跑下来最能看到纪律的一处：六个循环里只有两次真正红了（模块还不存在、折扣还没写），其余四轮测试写完直接就绿，子代理如实记下「无需新代码」——这正是「只写刚好够的实现」的自然结果，而不是一次把功能全堆出来等着测试验证。写测试前它还先验证了 200×0.9 在浮点数里是精确值，避免断言被舍入误差坑掉。

局限：技能要求动笔前先和用户确认「测在哪些接缝上」，本次接口直接来自需求，子代理视为已确认直接开工，这个确认环节在单轮派发下没有真正发生；另外零依赖约束下 Node 只剥离 TS 类型不做类型检查，属于场景约束的权衡，不是技能本身的问题。
