# retro

> 对一次编码会话做复盘。仅手动。

## 场景

前一天晚上让 agent 修一份技能文档的中文标点并加硬规则，第二天想复盘那次会话，看环境上有什么可以改进的。

## 对话

- /retro 复盘昨天晚上 22:54 左右那次会话（优化 .agents/skills/skill-tester/SKILL.md 的中文标点和硬规则那次），工作目录就是当前仓库根目录

  ```md
  复盘完成。我定位到目标会话（`~/.claude/projects/<本项目>/a6070798….jsonl`，11 月 4 日 21:21–22:54 本地时间），并独立核验了最终文件状态。以下是按严重程度排序的改进候选。

  ## 会话还原

  1. 21:21 用户请求：修正 skill-tester/SKILL.md 的中文标点 + 增加中文书写规范硬规则。
  2. 21:23 第一次 Write：**只加了硬规则，没有改标点**——文件当时仍含 106 处半角标点紧邻中文（我从日志里的 Write 内容重新扫描确认）。
  3. 随后连续 3 次 API 超时（22:05、22:11、22:51，每次约 40 分钟），约 90 分钟无进展。
  4. 22:54 第二次 Write：全文标点修正（重扫为 0 处违规），agent 自述「上一条 Write 只加了硬规则、还没真正修正标点」。

  ## 候选改进（按严重程度）

  **1. 自动化检查（高）——本次会话自己踩了这个坑，且仓库完全没有护栏**

  - 刚写进去的硬规则（`.agents/skills/skill-tester/SKILL.md:36`）本身是一条机械可检的标准（全角标点紧邻中文 = 违规，一行 grep 就能判），而第一次 Write 恰恰把这条规则写进了一个仍违反它的文件。检查在当时就是一行命令，却没跑——这是本次会话唯一真实的质量事故，自动检查可直接拦截。
  - 仓库现状：无 CI（无 `.github/workflows/`）、无 markdownlint、git hooks（在外层仓库的 `.git/modules/ai/hooks/`，注意本仓库是 submodule）里只有 Qoder tracker 的 post-commit/post-checkout，没有任何内容类检查。无护栏本身即一条发现。
  - 波及面：我用同一正则扫了全部已提交 markdown，**56 个文件共 723+ 处同类违规**，集中在 `turotials/agent/tool/*`（cron 79 处、workflow 73 处、task 58 处等）和 `libraries/models/voice/tts/README.md` 等。本次为单个文件确立的标准，全仓库文本并未遵循，且无任何东西强制。
  - 建议：装一个 pre-commit 钩子（装到外层仓库的 `.git/modules/ai/hooks/pre-commit`），对暂存的 `.md` 跑 `grep -nP '[\x{4e00}-\x{9fff}][,;:!?()]|[,;:!?()][\x{4e00}-\x{9fff}]'`；注意先剥掉围栏代码块再查，避免代码示例误报。这一条比在文档里再写一遍规则便宜且不会过期。

  **2. 供应商超时（高墙钟代价，仓库侧可做有限）**

  - 3 次 40 分钟级超时占了会话 90% 的墙钟时间。你的记忆里已有「model 覆盖会路由到无余额 stepfun 全员 429」的条目，但本次**没有**任何 override，属于同类的另一触发面：glm-5.3-flash 直连时的超时重试。记忆规则覆盖不到这种情况。
  - 建议：这条记到用户级 memory 更合适（如「连续 2 次 API 超时就停下告知用户，而不是静默重试到 40 分钟级」），仓库内无可落地动作。

  **3. 规则重复（低）**

  - `SKILL.md:36`（中文书写规范）和 `SKILL.md:41`（报告用中文）都带了「代码、命令、路径、错误信息保持原样/半角原样」这半句——同一含义两处维护。建议保留其中一处（建议留在 36 行，因为它是标点规范的母规则），41 行删掉这半句。skill 内该规则本身值得保留：它约束的是运行时生成的报告文本，检查够不着。

  **4. 无发现项**

  - Navigation / Information access：agent 一次 Read 就定位文件，无隐藏依赖，无缺失信息。
  - No-ops：硬规则清单除第 3 条的重复半句外，每条都改变行为，无空转指令。

  ## 正面确认

  最终文件状态通过独立机械检查（0 处半角标点紧邻中文），两次写入最终补全，agent 在 22:54 也如实自查出了第一次写入的缺口。

  优先级建议：先落第 1 条（pre-commit grep，一次性几行脚本，永久拦截），第 3 条是顺手的一行删除，第 2 条记入你的跨会话 memory。需要我动手实施其中任何一条的话告诉我。
  ```

## 依赖

- writing-for-agents：retro 第 1 步就要求调用它取写作风格指南，评估「编码标准」类改进时按它的原则决定规则写成什么形式；缺失时流程第一步即断。本环境已装，子代理实际加载了它。

## 总结

这个技能是会话结束后的「复盘会」：agent 回翻那次会话的日志，还原当时发生了什么，然后从几个固定角度（找文件顺不顺、缺不缺自动检查、规则有没有重复、哪些工具调用太贵）给你一份按严重程度排序的改进清单——改的不是那次会话本身，是让下次会话更好的环境。

这次用下来的感受是，它挖问题靠证据不靠感觉：它真的从日志里重新扫描了当时写入的文件内容，发现第一次写入漏改了标点（106 处违规原样留着）、却同时往文件里写进了一条标点规范——把规则写进一个违反规则的文件，这正是该被自动检查拦下的事故。顺着这条线它还查了仓库护栏（无 CI、无钩子），顺手扫出全仓库 56 个文件 723+ 处同类违规。每条建议都落在具体文件和行号，不泛泛而谈。

局限是它只给建议不动手：清单列完就停，要你明确说「实施第几条」它才会去改。另外复盘质量取决于会话日志还在本机，且它要自己去翻日志文件，这一段没有固定入口，找不找得到看运气。
