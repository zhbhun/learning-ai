# wayfinder

> 把一大块超出单次 agent 会话容量的工作，规划成 issue tracker 上一张由决策工单组成的共享地图，再逐张解决，直到通往终点的路清晰可见（仅手动）

## 场景

一个空项目目录里，用户想把「给单机 CLI 记账工具加多设备同步」这个方向未定的想法规划清楚再动手。

## 对话

> 对话原文中的本机绝对路径按隐私规则改写为相对路径（相对本报告目录）。

- /wayfinder 我做了个个人记账的命令行小工具，数据存在本地 SQLite 里，只有我自己在用。现在想让它支持多设备同步——手机上记一笔，电脑上也能看到——但用什么方式同步还没想清楚。项目放在 sandbox，代码还没初始化，想先把这件事规划明白再动手。

  ```md
  收到，进入 wayfinder 的"chart the map"模式。我先确认了环境事实：sandbox 目前是空目录（代码确实未初始化），位于 `learning/ai` 这个 git 仓库内；本会话没有配置专门的 issue tracker，按 skill 默认走 local-markdown tracker——地图会落在 sandbox 的 `.scratch/<effort>/` 下。这些不用你操心。

  先别急着建地图。按流程，第一轮先把"目的地"钉死，同时铺开整个决策面的前置问题。下面每个问题我都给了推荐答案，回复"都同意"即可整体接受；有不同意的单独指出即可。

  ❓ **Q1 - 地图的终点形态**：这次规划走到哪一步算"路已清楚"？(a) 产出一份同步方案 spec：选定架构、数据模型（含同步所需字段）、两端如何交互、离线与冲突策略，实现交给后续；(b) 只到"选定用哪种同步方式"这一个决定为止，细节以后再说；(c) spec 之外还要包含最小可运行实现。

  ➡️ 推荐 (a)：你说"先规划明白再动手"，(b) 太粗——同步方式和数据模型、离线策略是咬合在一起的，拆开选会返工；(c) 违背 wayfinder 默认的"规划不做"。选 (a) 即"是"。

  ---

  ❓ **Q2 - 手机端是什么形态**：工具现在是命令行，"手机上记一笔"意味着手机侧得有个录入入口。它是什么？(a) 自托管的轻量 Web 页面（手机浏览器用，可做成 PWA 加到主屏）；(b) 真正的手机 App（原生或跨端）；(c) 手机上也用命令行（如 Android 的 Termux）；(d) 手机端只做只读查看，录入仍以电脑为主。

  ➡️ 推荐 (a)：记账是低频简单交互，Web 页面开发成本远低于 App，又能跨 iOS/Android；Termux 对"随手记一笔"太重。(d) 会砍掉你说的核心诉求"手机上记一笔"，不建议。

  ---

  ❓ **Q3 - 离线要求**：手机没网时（地铁、飞行模式）必须能记账，之后联网自动补同步？还是接受"没网就不记"？(a) 必须离线可记，联网后同步；(b) 只在有网时记，接受在线写入。

  ➡️ 推荐 (a)：记账常发生在"刚花完钱"的当下，对网没有把握；而且本地 SQLite 本来就是离线的，离线优先并不增加多少成本。选 (a) 即"是"。

  ---

  ❓ **Q4 - 常驻服务器的意愿**：同步方案大体分"有个中心服务"和"无服务纯文件/CRDT 同步"两条路。你是否有一台愿意跑常驻小服务的机器？(a) 有现成的（VPS / NAS / 家里小主机）；(b) 没有，也不想为此维护服务器；(c) 没有自己的机器，但接受用托管服务（如 Supabase、Turso 这类免费档）。

  ➡️ 推荐：有现成机器就 (a)——记账是财务数据，自托管最可控且零额外成本；没有的话推荐 (c)，省运维且免费档对单人记账绰绰有余；(b) 会把我们推向文件同步或 CRDT 方案，代价是约束更多。

  ---

  ❓ **Q5 - 数据的变更形态**：记账条目基本是"只增不改"的吗？还是你会频繁修改历史记录（改分类、调整金额、删错账）？(a) 绝大多数只新增，偶尔改删——同步按"每条记录最后写入胜出"就够了；(b) 会频繁修改历史——冲突处理需要更认真的设计。

  ➡️ 推荐 (a)：个人记账的典型模式，LWW（last-write-wins）对单人场景足够，能大幅简化同步设计。选 (a) 即"是"。

  ---

  ❓ **Q6 - 现有代码的地位**：sandbox 是空的，已有的 CLI 代码和数据 schema 在别处吗？(a) 全新规划——数据模型也在这份 spec 里一起定，不受旧 schema 约束；(b) 已有代码/schema 固定存在，同步方案必须围着它设计。

  ➡️ 推荐 (a)：你说"代码还没初始化"，按全新规划处理，schema 可以直接为同步友好而设计（如每条记录带 `updated_at`、UUID 主键）。选 (a) 即"是"。

  ---

  这一轮答完，我会根据你的选择展开下一轮（同步触发时机、具体方案取舍、数据模型细节等被上面答案解锁的问题），然后建地图、拆 decision tickets。
  ```

## 依赖

- **grilling**：画图的问答引擎，目的地钉死与前沿铺开全靠它逐轮提问；缺失则流程第一步就走不动。
- **domain-modeling**：与 grilling 成对调用，负责消歧模糊口径（本例把「Q3 离线可记」与「网页不做离线缓存」的出入消解进地图 Notes）；缺失则歧义会直接带进地图。
- **research**：research 类型工单的执行引擎，派背景子代理按一手来源调研并落盘；缺失则 01 票无解，挡住其后的整串工单。
- **prototype**：prototype 类型工单的执行引擎，本轮只建票未解票，尚未实际出场。
- **local-markdown tracker 约定**：地图与工单的落盘格式（`.scratch/<effort>/map.md` + `issues/NN-<slug>.md`）；技能自带此默认，没有 setup 也不会断。

## 总结

当一个想法大到一次会话装不下、又还没想清楚怎么做时，wayfinder 不开工写代码，而是先画一张「路标图」：图上钉死目的地（这次规划做到哪算完），把路上所有要拍板的问题拆成一张张决策工单，标好谁挡着谁，说不清的问题先记在雾区；之后每次会话只解一张票，解掉一张解锁一批，雾散一路修一路，直到没有问题剩、只剩「去做」。没装它时（示意），这种大想法往往上来就动手，做到一半发现方案地基没定，返工；装了它，先被逼着回答六个边界问题（每个都带推荐答案，一句「都同意」就能过），然后一张地图、七张票、一份带一手来源的选型调研就摆在你面前了。

实际体验里最出彩的是两点：雾区不是摆设——调研结论一回来，「备份策略」等三个雾点立刻晋升成了正式工单；问答轮的消歧也真实发生了——「离线可记」和「网页不做离线缓存」的口径冲突被它抓住并写进了 Notes。局限也明显：HITL 问答会停住等人回复（本测试由主会话代答，子代理视角是「协调方消息」），一次会话只解一张票意味着整张图要走多个会话；另外按技能指示，research 资产会提交到抛弃型分支并推到仓库远端，在共享仓库里跑要留意这个副作用。
