# diagnosing-bugs

> 疑难 bug 与性能回归的诊断流程。当用户说「诊断/调试这个」或报告东西坏了、抛错、失败、变慢时使用。

## 场景

一个零依赖的 Node 小项目,发票日期格式化 CLI 把月份显示成了上一个月(`2024-05-15` 输出 `Apr 15, 2024`),请技能诊断并修复。

## 对话

- /diagnosing-bugs 我的项目在 sandbox/ 目录下,运行 `node index.js 2024-05-15` 输出的是 "Invoice date: Apr 15, 2024",月份差了一个,应该是 "May 15, 2024"。请帮我诊断并修复这个问题。

  ```md
  ## 根因

  `formatDate.js:8` 的月份索引 off-by-one：`d.getMonth()` 本身已返回 0-based 索引（May = 4），代码又减了 1，取到 `MONTHS[3]` = 'Apr'。所以任何日期都会显示成上个月。

  顺带发现并修复了同一函数里的**第二个潜伏 bug**：`new Date('2024-05-15')` 把 date-only 字符串按 UTC 午夜解析，在负 UTC 偏移的时区下（如 `TZ=America/New_York` 实测输出 `Apr 14`）日期会回退一天。你的机器是 +8 所以日没偏，只在月差上暴露了第一个 bug。

  ## 修复

  `sandbox/formatDate.js`

  - `MONTHS[d.getMonth() - 1]` → `MONTHS[d.getMonth()]`
  - date-only 输入改为显式按 Y-M-D 解析为本地时间，不再受时区偏移影响；非 date-only 输入仍走 `new Date(iso)`，无效日期照旧抛错

  ## 验证（按 skill 流程）

  - **Phase 1/2 回路**：`node index.js 2024-05-15`，修复前红灯输出 `Apr 15, 2024`（与你的症状一致）
  - **Phase 5 回归测试**：`sandbox/formatDate.test.js`（新增，`node:test`，零依赖）——修复前先跑确认红在用户症状上，修复后 3 个测试全绿，覆盖：报告的 bug、月边界（1 月/12 月）、时区偏移
  - **Phase 6 复验**：原始场景输出 `May 15, 2024`；`TZ=America/New_York` 下 `2024-05-15` 和 `2024-01-01` 均正确；无效输入仍抛 `Invalid date` 且 exit=1

  探针均为一次性 `node -e` 内联脚本，未在文件中留下任何 `[DEBUG-...]` 残留。改动未提交 git，如需我可以补一个 commit（message 里会写明假设 1 为确认根因）。
  ```

## 总结

这是个「先造红灯,再修车」的 debug 纪律技能:它不许 agent 一眼看代码就下结论,而是强制先造出一条能复现你症状的失败命令(反馈回路),红灯确认后再列假设、逐一验证、先写回归测试再改代码、最后清理探针。产出不只是修好的代码,还有留下来的回归测试。

实际试用里这套纪律肉眼可见地起了作用:agent 明明一开始就从代码里看出了嫌疑点,还是先按流程跑通了红灯回路;列假设时除了报告的月差 bug,还顺着第二条假设挖出同一行代码里潜伏的时区解析 bug(本机时区 +8 所以看不出来),一并修掉并补了测试。修复后主会话复验:原始命令输出 `May 15, 2024`,新增的 3 个回归测试全绿,目录里没有调试残留。一个局限:流程中「把假设清单亮给用户再继续」的环节,在单轮派发里 agent 按技能自带的兜底条款(用户不在场就按自己的排序继续)直接推进了,真实交互场景下这个检查点才能发挥换信息、重排序的价值。
