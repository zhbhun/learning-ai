Git 提交整理速查（rebase -i）

用途 整理自己 feature 分支上的提交 配套 第 1 课

一分钟心智模型

Rebase 整理提交 = 复制一份提交序列，按 todo 列表里的指示重放。原提交不会消失，只是不再有分支指着它们（约 30 天内可用 git reflog 找回）。

唯一铁律

不要 rebase 已经推送到 main 或别人也在用的提交。你自己的 feature 分支随便折腾。

todo 列表动词表

想做什么todo 里写效果
保留（默认）pick / p原样保留该提交
合并提交squash / s并入上一个提交，合并两条 message
合并且丢弃 messagefixup / f并入上一个提交，message 直接扔掉
修改 messagereword / r保留改动，打开编辑器改 message
调整顺序上下移动整行按列表顺序重放提交
删除提交删行 / drop / d该提交消失（改动也没了）
停下来改内容edit / e重放到该提交时暂停，改完 git commit --amend + git rebase --continue

列表顺序 = 提交先后，最旧在上，最新在下——和 git log 正好相反。

标准操作流

终端
git rebase -i HEAD~5        # 整理最近 5 个提交（数字 = 向前数几个）
#   编辑器打开 todo 列表 → 改动词 / 挪行 / 删行 → 保存关闭
#   git 逐条重放 → 全部完成后自动结束
git push --force-with-lease # 分支已推送过才需要；比裸 -f 安全
git log --oneline           # 验收

安全出口

终端
git rebase --abort          # rebase 进行中随时反悔，一步回滚，无残留

git reflog                  # rebase 已完成才发现错——HEAD 移动日志
# 找到 rebase (start) 前面的那条 hash：
git reset --hard <hash>     # 分支回到出事之前

更多事故急救（错 amend、错 reset、顶掉同事的提交……）：Oh Shit, Git 中文版。

安全规则（Julia Evans 实践总结）

  1. 一次 rebase 只做一件事——全 squash 就全 squash，改 message 就改 message，混着来最容易翻车
  2. rebase 开始后感觉不对 → 立刻 --abort，别硬着头皮走完
  3. push 已推过的分支用 --force-with-lease，别用裸 -f
  4. 永远不 rebase 已推到 main / 共享分支的提交
  5. 整理一大串碎提交：先 squash 压扁，再做其他 rebase（减少重放次数）

术语

todo 列表rebase -i 打开的编辑清单，一行一个提交，前缀动词指示动作
squash / fixup把一个提交并入上一个提交（fixup 丢弃 message）
reword只改 message，不改内容
reflogHEAD 的移动日志，找回“丢失”提交的钥匙
force-with-lease带检查的 force push——远端若被别人更新过则拒绝
重放rebase 把提交逐条复制重演，生成全新 hash 的新提交链
