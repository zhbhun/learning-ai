Git Rebase 课程 · 第 1 课

把碎提交整理成干净的历史

目标 学会 git rebase -i 的三个整理动作 用时 约 25 分钟 前提 会 commit、push、看 log

你的 mission 是提给团队的 PR 历史干净可读。这一课只解决其中最常见的一种乱：一个 PR 里躺着一串 wip、fix、fix typo。学完你能在自己的分支上把它们压成一个有完整描述的提交，改错 message，把顺序摆正——并且全程有后悔药。

遇到任何一步不清楚，回对话里问你的老师（我）。

安全声明

本课所有操作都只对你自己的、还没合并的分支做。整理这种分支是 rebase 最安全的使用场景。铁律只有一条：永远不要 rebase 已经推到 main 或别人也在用的提交。为什么，下一课讲。

一、rebase 到底做了什么（30 秒心智模型）

git rebase -i 的真相不是"修改历史"，而是：把提交复制一份，按你的指示重放一遍。 originals（原提交）不会被删掉，只是不再有分支指着它们。

17b7cb8docs: 报告框架和目录重放为新 hash
27faa82fix typo可被 drop 丢弃

两个直接推论：

推论 1：改动几乎不会丢。原提交在仓库里躺 30 天，git reflog 随时能捞回来（第三部分教）。

推论 2：hash 会变。重放生成的提交拿的是新 hash——所以别人基于你旧 hash 的提交会断掉。这就是"不要 rebase 共享提交"的根本原因。

二、第一次 git rebase -i（在真仓库里做）

练习仓库已经建好：/Users/zhanghuabin/Projects/learning/ai/practice-repo。它模拟了一个真实场景——一份调研报告的提交历史，前两个提交是正经的，后面五个是开发时的碎提交：

9e65b6caha 2最新
9288f76aha
27faa82fix typo要整理的
949c6f4wip要整理的
d028cc3fix要整理的
4e13e67wip 调研结果要整理的
bdf140ddocs: 团队分工页保留
17b7cb8docs: 报告框架和目录最旧

目标：把这 8 个变成 4 个——

?docs: 报告框架和目录不动
?docs: 团队分工页不动
?docs: 调研结果（初稿）4 个碎提交压成 1 个
?docs: 补充调研发现的第二个结论2 个 aha 合成 1 个
  1. 打开终端 cd /Users/zhanghuabin/Projects/learning/ai/practice-repo
  2. 跑 git log --oneline，确认你看到的 8 个 hash 和上面一致
  3. 跑 git rebase -i HEAD~6（往前数 6 个提交 = 从 wip 调研结果 开始整理；HEAD~6 表示“从当前往回数 6 个提交”）

编辑器会打开这样的 todo 列表（旧在上、新在下，和 log 相反）：

todo 列表
pick 4e13e67 wip 调研结果
pick d028cc3 fix
pick 949c6f4 wip
pick 27faa82 fix typo
pick 9288f76 aha
pick 9e65b6c aha 2

# Commands:
# p, pick <commit> = use commit
# r, reword <commit> = use commit, but edit the commit message
# s, squash <commit> = use commit, but meld into previous commit
# f, fixup <commit> = like "squash", but discard this commit's log message
# d, drop <commit> = remove commit

改三处，保存关闭编辑器：

改完的 todo
reword 4e13e67 wip 调研结果      → 改 message 为「docs: 调研结果（初稿）」
fixup d028cc3 fix
fixup 949c6f4 wip
fixup 27faa82 fix typo
reword 9288f76 aha           → 改 message 为「docs: 补充调研发现的第二个结论」
fixup 9e65b6c aha 2

注意这里没有 drop——四个碎提交不是被扔掉，而是被 fixup 吸进了上一条。它们的改动保留，message 丢弃。存盘退出后 git 会依次弹出编辑器让你为两条 reword 输入新 message，然后自动走完。

完成后跑 git log --oneline 验收，应该恰好 4 条，且旧提交 hash 17b7cb8、bdf140d 不变（它们没被重放），其余全部换成了新 hash。

验收标准

git log --oneline 输出恰好 4 行，最后两行的 hash 是 bdf140d 和 17b7cb8（从旧到新）。做到即过关。

三、浏览器模拟器（零风险试错）

如果你还没在终端里做过第二部分，或想先无成本试错——下面的模拟器行为和真 git 一致（drop 会真丢弃、squash 需要上一行活着、reword 弹输入框）。目标同样是 8 → 4。

四、安全出口：两个救命命令

git rebase --abort

rebase 进行中任何时候反悔——冲突解不动、todo 写错、单纯心慌——跑这一句，一步回到 rebase 开始前，无任何残留。这是你唯一的"退出键"，比试图"修好"靠谱得多。

git reflog

rebase 已经走完才发现错了呢？用 reflog。它是 HEAD 的移动日志：

终端
git reflog
9e65b6c (HEAD -> main) HEAD@{0}: rebase (finish): returning to refs/heads/main
...
e3f4a5b HEAD@{5}: rebase (start): checkout HEAD~6
9e65b6c HEAD@{6}: commit: aha 2
9288f76 HEAD@{7}: commit: aha

找到 rebase (start) 前面那条（例中 HEAD@{6} 的 9e65b6c，即 rebase 开始前 HEAD 所在的提交），然后：

终端
git reset --hard 9e65b6c
HEAD is now at 9e65b6c aha 2

整个分支回到出事之前，仿佛什么都没发生。详细原理与更多事故急救见 速查手册 · 自救章节。
